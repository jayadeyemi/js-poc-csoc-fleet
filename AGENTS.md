# js-poc-csoc-fleet

**Authoritative inventory of every cluster the CSOC operates.** Adding a cluster = opening a PR here. No scripts, no Helm charts — only `SpokeCluster` CRs and optional `applications.yaml` sidecar files.

GitHub: `github.com/jayadeyemi/js-poc-csoc-fleet`

## Repo layout

```
customers/
  <customer-id>/
    <environment>/
      cluster.yaml          SpokeCluster instance (required)
      applications.yaml     optional app assignments for this cluster
csoc/
  management/               CSOC-internal management cluster registration
  shared-services/          shared services cluster(s)
```

## Adding a spoke cluster (day-2 operation)

1. Create `customers/<customer-id>/<env>/cluster.yaml` from the example below.
2. Optionally create `customers/<customer-id>/<env>/applications.yaml`.
3. Open a PR → merge → Argo CD applies the `SpokeCluster` CR → KRO provisions → cluster appears.

### `cluster.yaml` template

```yaml
apiVersion: csoc.js2.org/v1alpha1
kind: SpokeCluster
metadata:
  name: <customer-id>-<env>           # must be globally unique across ALL customers/
  namespace: spokeclusters
spec:
  environment: <dev|staging|prod>
  provider: openstack
  kubernetes:
    version: "1.29"
    nodeClass: general
    minNodes: 2
    maxNodes: 5
  network:
    connectivity: public
  capabilities:
    security: false
    observability: false
  registration:
    labels:
      csoc.js2.org/customer: <customer-id>
      csoc.js2.org/environment: <env>
```

### `applications.yaml` template

```yaml
cluster: <customer-id>-<env>
applications:
  - name: gen3
    release: "2026.08"
```

## Naming rules

- `metadata.name` must be **globally unique** across the entire `customers/` tree. Use `<customer-id>-<env>` — no exceptions.
- Customer IDs are lowercase, alphanumeric, hyphen-separated (e.g. `university-a`, `nci`, `research-project-x`).
- Environments: `dev`, `staging`, `prod` only.

## Cluster labels

Argo CD ApplicationSets react to these labels on the registered cluster secret:

| Label | Effect |
|-------|--------|
| `csoc.js2.org/type: spoke` | Always set by registration controller; triggers baseline ApplicationSet |
| `csoc.js2.org/security: enabled` | Triggers security ApplicationSet |
| `csoc.js2.org/observability: enabled` | Triggers observability ApplicationSet |
| `csoc.js2.org/gen3: enabled` | Triggers Gen3 app deployment |

To enable a capability for a cluster, add the label in `registration.labels` in `cluster.yaml` **and** ensure the corresponding app exists in `js-poc-csoc-app-catalog`.

## Ownership modes

| Mode | `cluster.yaml` field | Who manages apps |
|------|----------------------|-----------------|
| CSOC-managed | `ownership: csoc` | CSOC via `applications.yaml` |
| Customer-managed | `ownership: customer` | Customer's own GitOps |

## Pitfalls

- **Do not put CAPI objects here.** `cluster.yaml` is a `SpokeCluster` CR, not raw CAPI YAML.
- **Do not put Argo `Application` objects here.** Those are generated by ApplicationSets in `js-poc-csoc-bootstrap`.
- **`metadata.name` collisions** will cause KRO to reconcile the wrong cluster. Check existing names before creating.
- Removing a `cluster.yaml` does **not** automatically delete the spoke cluster — deletion must be a deliberate, gated operation. Add a note in the PR.
